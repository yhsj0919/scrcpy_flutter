## 功能里程碑

### M0：技术验证

- 固定 scrcpy 和 FVP/libmdk 版本。
- 在 Windows 上连接一台开启 USB 调试的 Android 设备。
- 使用 `raw_stream=true` 启动 `scrcpy-server`。
- 将数据送入 FVP 并显示第一帧。
- 测量启动时间、延迟、CPU、GPU 和内存。
- 旋转设备并记录播放和纹理行为。

完成标准：Flutter 组件能够持续显示视频，且不通过 Dart 搬运每帧像素。

### M1：可控制的嵌入式会话

- 设备发现和选择。
- 会话启动、停止、断开和错误状态。
- 触摸及鼠标坐标映射。
- 点击、拖动/滑动、滚轮、返回、主页和键盘输入。
- 自动重连和设备旋转处理。
- 可用的单设备示例页面。

完成标准：单台设备能够长时间稳定显示和控制。

### M2：设备墙原型

- 多个独立设备会话。
- 响应式网格和聚焦设备视图。
- 每个格子的状态、重连和生命周期隔离。
- 根据可见性动态调整 FPS 和分辨率。
- 测试 1、4、8、16 台设备的资源占用和稳定性。

完成标准：根据实测确定并发设备数量，并确保单个会话故障不会影响整个设备墙。

### 后续功能

- 剪贴板同步和文本输入。
- 聚焦设备音频。
- 屏幕录制和截图。
- 文件推送、安装及拖放。
- TCP/IP 设备和远程 ADB。
- 带安全控制的群控/输入广播。
- Linux 和 macOS 主机支持。

## 开始实现前仍需决定

以下内容先采用推荐默认值，技术验证失败时再调整：

1. scrcpy 暂定固定在 **4.1**，server 与控制协议代码必须使用相同版本。
2. FVP 暂定固定在 **0.38.1**。第一版使用仓库内可审查的小补丁暴露 `appendBuffer`，验证通过后再决定是否提交上游。
3. 第一版只承诺 **Windows**；其他平台注册代码暂时保留，但在文档和 API 中标记为不支持。
4. 设备墙稳定目标为 **8 台**，同时对 **16 台**进行压力测试，不在实测前承诺 16 台稳定运行。
5. 第一阶段只使用 USB ADB、H.264 和无音频模式。

## 推荐开发计划

以下估算按一条主开发线计算，是有效开发日而不是自然日。真机兼容性和硬件并发问题不包含在固定承诺中，通过阶段验收门控制。

| 阶段 | 预计投入 | 主要产出 | 验收门 |
| --- | ---: | --- | --- |
| P0 工程基线 | 1–2 天 | 固定依赖版本、整理 Windows-only 支持范围、定义基础 API、建立日志和错误模型 | `flutter analyze`、现有测试和 Windows 示例构建通过 |
| P1 视频技术验证 | 3–5 天 | FVP `appendBuffer` 扩展、raw H.264 输入、Flutter 纹理显示 | 真机首帧成功，连续播放 30 分钟，无逐帧 Dart 像素复制 |
| P2 ADB 连接与会话生命周期 | 5–8 天 | USB/网络/配对码连接、server 部署、停止和资源回收 | 三种连接方式可用；重复启停 50 次无残留资源 |
| P3 scrcpy 控制闭环 | 6–9 天 | 模拟触摸、多指、导航键、键盘、剪贴板、画质和坐标映射 | 横竖屏下输入准确，连续操作无控制流错位 |
| P4 单设备稳定版与 S1 管理 | 核心 4–6 天；S1 6–12 天 | 热插拔、重连、设备详情、文件、状态和批量安装/卸载 | 2 小时稳定运行；S1 功能分别通过验收 |
| P5 设备墙、批量控制与多开 | 8–14 天 | 多 Session、网格、批量框架、触摸广播验证和虚拟显示 | 4 台稳定运行；多开形成兼容性报告 |
| P6 性能调度与压测 | 5–10 天 | 可见性降帧、分辨率策略、资源监控、8/16 台报告 | 8 台达到稳定目标，形成 16 台压测结论 |
| P7 发布准备 | 2–4 天 | API 文档、示例、许可证清单、打包和升级说明 | 可从干净环境构建并运行示例 |
| P8 移动端、鸿蒙与 Web 可行性 | 后期独立排期 | Android 宿主、鸿蒙宿主控制 Android、iOS 限制调查、WebUSB/WebCodecs、代理网关 | 各平台分别作继续、有限支持或终止决定 |

Windows 主线预计总投入：**40–70 个有效开发日**。其中 S0“连接—画面—控制—单设备稳定”约 **19–30 天**；S1 设备管理约增加 **6–12 天**；设备墙、批量控制、多开和性能验证约 **13–24 天**；发布准备约 **2–4 天**。P8 移动端与 Web 不计入该估算，待 Windows API 稳定后分别评估。M0（出现第一帧）在 P1 结束时完成，设备墙可用性由 P6 实测决定。

## 任务依赖顺序

```text
工程基线
  -> FVP 内存流与纹理
      -> ADB/scrcpy 会话生命周期
          -> 控制与坐标映射
              -> 单设备稳定性
                  -> 多会话设备墙
                      -> 性能调度与发布
```

不建议在 P1 视频链路和 P2 资源回收稳定前并行开发设备墙 UI，否则多设备问题会掩盖单会话生命周期问题。

## 每阶段必须记录的指标

- 从启动 server 到 Flutter 第一帧的时间；
- 输入到画面响应的端到端延迟；
- 每台设备的 CPU、GPU、内存、线程和显存增量；
- 视频实际分辨率、FPS、码率及使用的解码器；
- 启停、旋转、拔插、断流后的恢复结果；
- 1、4、8、16 台设备下的总资源占用与掉帧情况。
