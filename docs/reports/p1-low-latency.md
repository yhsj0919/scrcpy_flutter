# P1 原生低延迟视频后端验收报告

## 结论

- [x] scrcpy codec/session/frame metadata 在 Dart 层拆包并保持 PTS。
- [x] H.264 在 Windows Media Foundation 原生侧解码。
- [x] NV12→RGBA 在原生独立线程执行，不向 Dart 逐帧传输像素。
- [x] 转换队列只保存最新待转换帧，积压时覆盖旧帧。
- [x] Flutter 通过 Texture 接收最新像素帧。
- [x] 首帧和控制到画面变化延迟均可自动测量。
- [x] 连续 20 次控制闭环无协议错位或不可恢复错误。

P1-03 单设备技术闭环通过。D3D11 硬解与零拷贝根据基线结果列为 P7 多设备验收前置优化。

## 控制到画面变化延迟

- 日期：2026-09-02
- 设备：Xiaomi 23127PN0CC，Android 16
- 视频：H.264、最大 1920 px、60 FPS、8 Mbps
- 样本：20 次，交替发送 Recent Apps 与 Back

| 指标 | 结果 |
|---|---:|
| 平均 | 178.96 ms |
| P95 | 318.75 ms |
| 最小 | 5.00 ms |
| 最大 | 360.01 ms |

测试入口：`example/integration_test/control_latency_test.dart`。

原生后端为每个完成转换的 RGBA 帧计算 32×32 级稀疏画面指纹，并记录 `QueryPerformanceCounter` 时间。测试等待画面稳定后记录控制发送前的同源高精度时钟，发送按下/抬起消息，再等待指纹变化，以变化帧完成时间计算闭环延迟。

该指标包含控制 socket、Android 输入处理、系统界面动画、编码、ADB 转发、解码、颜色转换和 Texture 通知。它是用户可感知闭环延迟，不是纯解码耗时。5 ms 最小值可能来自系统动画在控制边界附近已经产生的新画面，因此判断主要参考平均值和 P95。

## latest-frame 证据

- NV12 解码帧进入单槽 `pending_nv12_`；转换线程来不及时，新帧覆盖旧待转换帧。
- 第二轮 30 秒基线收到 1684 个解码输入并显示 299 帧，视频保持实时且无队列无界增长。
- RGBA 缓冲区仅存在于 Windows 原生 Texture 对象，MethodChannel 只传包数据、控制信息和少量统计值。

## D3D11 决策

当前 Debug 单路基线的归一化 CPU 为 10.76%，主要成本包含软件 Media Foundation 解码和 CPU NV12→RGBA。单设备首版可以接受，但按此成本线性扩展无法满足 8～16 台设备墙。

因此：

- P1 不以 D3D11 阻塞单设备原生视频闭环。
- P7 增加 D3D11 硬件解码/共享纹理或等效零拷贝任务。
- P7-03 八设备验收必须在该优化完成或明确证明无需优化后执行。
